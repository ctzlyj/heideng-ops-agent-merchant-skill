# 商家体验只读审查与准备修改清单（2026-11-18）

## 基线与边界
- 当前源码/默认分支：0.4.3 / 0238829aba00689aaf339239caab6c37d7694e14，工作区干净。
- 只读审查实际SKILL、经验导航、连接、素材、短标题、上架、采集、比价、视频与更新路径；未改代码、未发布。
- 保持：宿主Agent规划、黑灯经验导航和成熟工具；不新增业务调度/审批引擎，不改生图提示词，不读公司凭据。
- 本文件不是宣称已完成这些修改，也不是宣称真实商家全链路已验收。

## 一、优先修改：统一商家可见状态和恢复入口

**证据**
- `heideng_merchant/cli.py` status输出完整来源/commit/blocker列表；install输出大量嵌套JSON。
- `mature_runtime.py::run`直接透传子进程stdout/stderr；业务错误常为错误码/长traceback。
- 素材最终大量明细已有`.state/merchant-result-auto-maintain.json`，但没有面向宿主的简洁统一摘要。
- 更新usage begin/heartbeat/end需要宿主手工协调，和run安装锁是两套使用证据。

**准备修改**
- 增加薄的“商家状态投影”：安装成功、已连接、正在等待登录、正在生成/上传、等待平台审核、需要本人处理、可恢复、已完成分别给一句话、下一动作和结果文件。完整原JSON保留供工具/排障，不把技术输出隐藏为不可诊断。
- 统一错误分类：本人登录/风控、平台权限/审核、网络可恢复、环境缺依赖、范围或事实缺失、结果未知需原回执核对；禁止unknown变成failed/no-write。
- 将usage标记集成到实际run/控制器生命周期，避免依赖每个宿主自觉手工调用；当前任务继续旧版本，后续任务刷新规则保持。

## 二、优先修改：连接断点默认恢复与多店会话

**证据**
- `mature/connection/app/server.py::start_flow`普通同店重试跳过旧failed/mismatch，只有显式`--resume`恢复原job。
- `host_connection_controller.py`单一`browser-controller/session.json`绑定shopIdentity，跨店需要新的目录，商家多店切换理解成本高。
- `BrowserAuthJob.resume`可核验已有结果再恢复，不需要每次从零开始。

**准备修改**
- 同店同Profile的等待/网络中断/登录超时，默认恢复原任务；先核验已有Profile/OAuth结果，不重复点击/扫码。
- 明确`重新开始`才创建新会话；身份mismatch/凭据隔离/未知结果不得静默复用。
- 按店铺隔离保存context/profile/channel和最近可用状态，切店只切目标，不串店；同店连接后的Profile自动给短标题/素材使用。

## 三、优先修改：长任务进度、离开与审核等待

**证据**
- `generate_batch`保存task/job结果，`stage_timer`只记录阶段耗时；自动维护在素材绑定后串行短标题导入、属性和回读。
- `execute_material_binding_plan`已区分submitted/pending/approved/failed，但用户体验只看到长等待或最终JSON。
- `run_auto_maintain`回查异常被简化为verification-unavailable；短标题回读不可用时提示nextAction但缺统一分类。
- 素材审核pending并非失败，也不应不断重新绑定。

**准备修改**
- 复用原task.json/stage/receipt提供“已完成X/Y、当前阶段、预计是否还要付费、可以离开、稍后如何恢复”的只读摘要；不新建队列或业务定时任务。
- 审核中采用有界回读与明确等待状态；已经提交的不再为等待审核而重复生成/上传/绑定。
- 阶段衔接保留真实回执；失败阶段不抹掉前面成功结果。批量任务复用一次范围盘点和分阶段结果，减少无意义重复全店回读。
- 连接和素材长等待时宿主能够告知用户离开/继续，不让其不断发送“好了吗”。

## 四、执行体验与首次使用减负

**证据**
- `references/experience-materials.md`同时包含原则、多个历史版本适配和参数细节，宿主加载成本高。
- JSON agent-text与XLSX导入表已经区分，但仍靠宿主准确理解大量命令/路径/参数。
- 安装依赖准备可能耗时，成功/降级信息与技术能力清单混在一起；视频外部生成未配置等边界混在通用介绍里。
- 更新worker detach与连接服务detach模式需要一致，否则WorkBuddy进程回收仍可能失去后台检查。

**准备修改**
- 将经验页分成“商家任务短指南”与“维护者技术附录”：先目标/需要事实/下一动作/结果，参数与历史说明后置，减少宿主误用。
- 首次使用由状态投影给“可以连接店铺/还缺哪一步”，不把所有来源commit和内部blocker倾倒给商家。
- 更新后台进程采用原连接器已验证的跨平台detach方式，状态不可达不影响原业务，只有持续失败/本人授权时提示。
- 未配置的视频生成、外部视觉等只在该任务需要时提示，不把只读/已有素材/本地交接也挡住。

## 五、随后处理：恢复型结果与反馈
- 申诉/驳回结果直接区分“平台审核问题可申诉、图片字节/抠图损坏可修复、真实商品内容需人工处理”，商品本体文字不重生不改提示词。
- 交付给商家的是已完成数、待审核数、需本人处理数与可打开的结果文件，不是几十万字明细。
- 单次恢复自动列出原任务与原回执位置、不会重复哪些提交；不让商家手工拼reconcile命令。
- 保持成熟工具的来源/哈希、店铺身份、Profile隔离、费用与范围确认、未知结果保护。

## 推荐实施顺序
1. 商家状态/错误投影 + 实际usage生命周期；先把可读性和恢复事实统一。
2. 同店默认恢复 + 多店会话绑定；解决连接反复开始和跨店切换。
3. 长任务进度/审核等待/可离开；复用原状态不重建引擎。
4. 经验短指南、安装更新与结果交付减负。

每项只做必要局部适配和对应离线/隔离验证；真实扫码/OAuth/付费与店铺写入继续需用户安排内测。
